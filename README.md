# aifu.plus — 账号充值 + 卡密发货（支付宝当面付）

开发归属与协作记录见 [DEVELOPMENT_ATTRIBUTION.md](DEVELOPMENT_ATTRIBUTION.md)。

技术栈：Python 3.9+ / Flask / SQLite（WAL）/ Jinja 模板 + 一份 CSS。买家全程不需要注册登录。

## 安装与启动
```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m app.migrate                                        # 数据库迁移（可重复执行；--status 查看）
.venv/bin/python -m app.manage create-admin --email you@example.com    # 创建管理员（只有管理员需要登录，入口 /admin）
.venv/bin/python run.py                                                # 启动网站 + 后台定时任务线程
.venv/bin/python -m pytest -q                                          # 测试（全部使用测试替身，不会真实扣款/充值）
```
- 数据与密钥在 `instance/`。**务必备份 `instance/keys.json`**（加密主密钥；丢了就无法解密已存的支付宝私钥、卡密和账号会话）。
- 多进程部署时另起 `python -m app.worker`，负责超时关单、主动查单、充值重试与轮询。
- 所有密钥、网址、客服信息都在后台页面里填，不需要改配置文件。

## GPT 直充定价（地区差异定价 + 自动成本同步）
- 只开放四个套餐：Plus（`plus-monthly`）、Pro 5x（`pro5x-monthly`）、Pro 20x（`pro20x-direct-monthly`）、Pro Max（`promax-monthly`）。每个「套餐 + 地区」是独立规格（表 `plan_variants`），可单独上下架、单独定价。
- 成本：上游 `/config` 的 `wallet.prices`（美元参考成本；`null` 不是 0，保留最后一次有效值）；`planRegions` 是可售地区；`regionalDisplayPrices` 被忽略。上游参考成本**必须由管理员点「采用」后**才会成为有效成本；也可以填人工人民币成本。从未有成本的地区不能上架。
- 汇率：`app/fx.py` 的 provider（frankfurter.dev → open.er-api.com，HTTPS、无 Key、有超时）；失败保留上一次汇率；可人工覆盖；可设安全系数。
- 公式（全部在 `app/pricing.py`，整数分/美分/百万分之一汇率/基点）：套餐成本 = 美元成本 × 实际汇率（或人工人民币成本）；总成本 = 套餐成本 + 其他成本；百分比加价：总成本 ×（1+p）；固定利润：总成本 + 利润；取整：两位小数 / 向上取整到元 / 尾数 .90 / 尾数 .99（只向上调整）。
- 保护：成本或汇率相对上次变化超过阈值（默认 10%）→ 暂停自动调价、标记「等待确认」；同步超过 2 小时黄色警告、超过 6 小时红色警告；所有同步和调价写入 `pricing_audit`。
- 定时：只有独立的 `python -m app.worker` 进程会在启动时同步一次、之后每 30 分钟同步（数据库锁保证不会重叠）；Gunicorn Web 进程不跑定时同步，管理员点「立即同步」时用同一把锁。
- 订单在下单时固化价格、成本、汇率、定价方式和预计利润，之后任何调价都不影响历史订单。

## 管理员怎么用（全部在 /admin，中文卡片界面）
| 页面 | 做什么 |
| --- | --- |
| 首页 | 开店清单（配置收款、连接上游、同步套餐、创建商品）+ 需要处理的订单 |
| 支付宝收款 | 沙箱/正式、App ID、商户编号、密钥、公网网址、付款时限，一键测试 |
| 上游充值 | 状态卡片（连接/自动充值/密钥/卡台/最近同步）→ 保存配置 → 测试连接 → 同步套餐 → 套餐卡片「创建为本站商品」 |
| 商品与定价 | 四张套餐卡片（已上架地区数、最低售价、最近同步、定价策略、异常）→ 展开地区管理（上下架、成本、加价、批量设置、确认异常）；汇率与保护设置；卡密商品的创建与库存 |
| 订单 | 按「待付款/处理中/需要处理/已完成/已关闭」筛选；订单页用人话解释现状，只有一个主按钮 |
| 网站内容 | 客服微信与时间、页脚声明、账号会话获取步骤、常见问题、退款说明、条款与隐私 |

技术字段（套餐标识、上游订单编号、错误代码等）只出现在折叠的「高级信息 / 技术详情」里。

## 买家流程（无需账号）
选择商品 → 填写资料 → 确认订单 → 支付宝付款 → 自动充值/发货 → 查看结果。
- 下单后得到不可猜测的专属链接（`?t=` 令牌），它是游客查看订单（含卡密）的唯一凭证。
- 「查询订单」需要同时填订单号 + 下单邮箱，只能看到进度；**卡密不会通过查询页显示**，只有专属链接（或管理员创建的账号登录）能看。

## 资金与履约规则
- 支付：异步通知验签 + `alipay.trade.query` 补查共用同一个幂等入口；超时先查单再关单；迟到付款保留记录并继续履约，库存不足则显示原因，补货后自动发货。
- 充值：固定「自动选卡」付款方式；超时先按订单编号查单，确认上游没创建才用同一编号重提；结果无法确认的转人工，不会自动重提。
- 卡密：加密保存、HMAC 去重，下单预留库存，付款后事务内绑定，不会超卖。

## 限制与需要你知道的
1. 上游文档没写全 `/config`、任务详情、任务列表的响应结构，代码做了容错解析；认不出来就转人工或提示，不会当成功。**首次接真实上游请先小额试一单。**
2. 文档没有教买家如何获取「账号会话信息」，请在后台「网站内容」写上你们实际的步骤。
3. 没有退款接口，也没有实现支付宝退款：库存不足、充值失败的订单请在支付宝后台人工退款。前台只有在你填写了「退款说明」后才会显示「开通失败可退款」。
4. 不支持：微信支付、Cloudflare Turnstile、支付宝证书模式。
5. 前台用的是 Jinja + CSS，没有用 Next.js / shadcn/ui（后端是 Flask，机器上没有 Node）。字体里的拉丁字母和等宽数字已自托管（Source Serif 4 / Source Sans 3 / IBM Plex Mono，SIL OFL）；中文字体（思源宋体/黑体）按「本机已安装则用，否则回退到系统字体」处理，需要的话可以另行自托管子集。
6. 主按钮 `#C26A1A` 配 `#FFFDF8` 文字，对比度约 3.8:1，低于 WCAG AA 的 4.5:1（粗体 17px 勉强算大字号）。如需严格达标，可把按钮底色换成悬停色 `#A35512`。
